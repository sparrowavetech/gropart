# Indian GST implementation audit — 2026-11-01

## Scope and evidence

Read-only inventory of all 31 files under `platform/plugins/indian-gst`, with focused review of its PHP, routes, migrations, views, invoice template, asset, language and manifest, plus the relevant Farmart Helper wholesale adapter and effective local invoice template. Live GPINV-758 data/model/helper evaluation was read-only over SSH. Local standalone helper reproduction and PHP syntax checks were performed. No application code, database, invoice or live deployment was changed. Local plugin routes were unavailable in the current local app boot, so admin/browser and end-to-end checkout behavior remain unverified.

## Confirmed defect: GPINV-758

Live invoice 758 references order 19580; seller store and shipping address both save state `30`. Location `states.id=30` is Rajasthan. `IndianGstInvoiceListener` passes the seller's raw `30` but the customer's resolved `state_name` `Rajasthan`. `IndianGstHelper::normalizeState` treats numeric `30` as GST code Goa before trying the Location state ID. Live and local helper evaluation produce `goa` versus `rajasthan`, hence `isIgst=true`. The total tax amount (₹526.12) was not recalculated in this audit; the proven issue is the displayed IGST/CGST/SGST classification.

## Independence assessment

Business tax code uses Ecommerce models and hooks, and has no direct Farmart theme class reference. Marketplace and Location use conditional checks in some paths. It is **not yet portable** to any Ecommerce theme: checkout DOM manipulation and admin URL are layout-specific, invoice template contains Gropart-specific identity, Location ID/GST code handling is ambiguous, and the optional Wholesale binding has not been isolated across activation combinations. No claim of Nest/Shofy compatibility is supported by tests.

## Proposed implementation sequence (not started)

1. Introduce explicit state resolvers: Location state ID from typed store/order address fields when Location is active, saved state name/code otherwise, configured seller state when Marketplace is off. Compare canonical Indian GST codes; treat unresolved states as a surfaced validation/review condition. Add GSTIN prefix consistency checks without silently changing issued invoices.
2. Remove business-specific legal defaults and activation overwrites. Use explicit validated settings, Ecommerce company settings as documented fallback, and typed state/GSTIN validation. Keep saved economic snapshots intact.
3. Fix invoice component allocation to paise with exact sums; verify invoice variables/template against total, shipping tax, fees, discounts, quantity, inclusive/exclusive and multi-vendor cases. Preserve custom storage template; provide a deliberate upgrade path rather than overwriting it.
4. Align the enable/inclusive settings with actual behavior. Audit slab table calculations against Ecommerce tax configuration, product flags and sale/variation prices. Remove misleading fallback calculations.
5. Separate GST responsibilities from marketplace vacation/shipping UI where feasible without touching upstream code. Make optional plugin interactions guarded and test binding order with Farmart Helper/Wholesale enabled and disabled.
6. Give every admin action a canonical permission with valid parent and matching menu/route checks; test non-super-admin access. Move UI strings into symmetric English/Hindi plugin language files and remove hardcoded routes/DOM polling. Use standard Ecommerce hooks for theme-neutral output; allow graceful absence of layout-specific placement.
7. Add focused plugin-owned tests, then local disposable fixtures for admin order create, checkout, incomplete/complete order, invoice/PDF, customer storefront, Marketplace on/off, Location on/off, tax setting combinations and multiple themes. Only after local results are reviewed should a separate authorized live deployment plan be made, with backup and invoice-specific correction decision.

## Local implementation update — 2026-11-01

The user authorized a local-only fix after the audit. Application changes are confined to `platform/plugins/indian-gst/` and its previously identical, plugin-published local invoice template at `storage/app/templates/ecommerce/invoice.tpl` (ignored by Git). Live code/data remain unchanged.

- Invoice state comparison now uses Ecommerce's resolved seller/customer state names, honors the billing address when configured, and uses a valid seller GSTIN prefix as the seller tax origin. Numeric Location IDs are resolved before GST codes only when the Location integration is active in Ecommerce. Missing jurisdiction is displayed as generic tax rather than silently claiming intra-state CGST/SGST. This addresses GPINV-758's `30`/Rajasthan collision without changing saved invoice tax amounts.
- Inclusive tax amounts are split in integer paise, and the plugin invoice template displays exact item/total CGST and SGST. The published local template was updated only after confirming it was byte-identical to the bundled original. Existing customized templates on other installations must be reviewed separately; activation no longer overwrites them.
- Business-specific default GSTIN, identity, address, phone, logo and Rajasthan fallback were removed. Ecommerce invoice settings supply fallback values. Activation preserves existing settings; uninstall preserves business data. The unused display-inclusive setting was removed from the form. GST enablement now gates inclusive bindings/listeners.
- The slab table uses each product's inclusive flag and no longer assumes a default 18% when the slab is missing. Theme-specific DOM polling, fixed `/admin` link and no-op shipping hook were removed; checkout item label uses a standard Ecommerce hook. Ecommerce is a manifest requirement; Marketplace/Location remain conditional. Permissions were linked to the Ecommerce tree and settings routes now declare their permission. English/Hindi plugin language files have symmetric keys; plugin views, menus and invoice labels reference them.
- A plugin-owned standalone regression script covers the Location ID collision, same/different state, Location off/code fallback, GSTIN origin, odd-paise allocation and locale symmetry. It passed 9/9. A plugin-owned Twig template fixture passed 2/2 checks for exact odd-paise split and unknown jurisdiction labeling. All plugin PHP syntax checks and `git diff --check` passed. Static inspection found 0 orphan permission parents and 0 missing referenced translation keys.

Limits at the initial implementation check (superseded by the runtime section below): local DB access and plugin routes were unavailable then. Existing invoice PDFs may be cached, and published/custom invoice templates need a deliberate live migration plan. Do not deploy or repair GPINV-758 from local verification alone. The historical GST state-code mapping and optional plugin combinations still merit compatibility checks before claiming universal portability.
